# rmoddel.com — GSD Execution Plan

## 1. Project Objective

Rebuild **rmoddel.com** into a coherent personal career site with three complementary experiences:

1. **A concise landing page** that explains who Reuben is, what he does, and why he is valuable within five seconds.
2. **A conventional résumé page** that remains scannable, printable, downloadable, and easy to share.
3. **A full-page ChatGPT-style interactive résumé** where visitors can explore Reuben’s experience, strengths, projects, leadership approach, AI capabilities, values, and fit for an opportunity.

Support these with:

- `/about` — career story, work ethic, human understanding, leadership philosophy, AI philosophy, and GPS.
- `/contact` — a direct standalone contact path.
- Optional `/work` and case-study pages for real project proof.

The site should feel like one intentional product—not a résumé site, consulting site, AI agency, and creative portfolio competing with one another.

## 3. GPS — Genuine, Personalized Solutions

GPS is the organizing philosophy of the site.

### Genuine

Solve a real problem and produce a real, usable result.

This means:

- No AI added merely for appearance.
- No generic chatbot attached to a process without a reason.
- No prototype presented as a finished operational solution.
- No technology searching for a problem.

Preferred language:

> Built around a real problem, a real workflow, and a result people can actually use.

Avoid repeatedly saying “no fake AI.” Communicate authenticity positively.

### Personalized

Design around the organization’s actual:

- Workflow
- People
- Terminology
- Rules
- Priorities
- Existing systems
- Level of technical comfort
- Routine decisions and variables

Preferred language:

> Your process should shape the software—not the other way around.

Personalized does not mean every underlying component must be written from scratch. It means the complete solution is intentionally designed and configured for the client’s needs rather than forced into a generic off-the-shelf workflow.

### Solutions

Deliver a practical outcome, not merely advice or a technical demonstration.

Possible outcomes include:

- Internal tools
- AI-enabled workflows
- Workflow automation
- Document intelligence
- Self-service generators
- Dashboards
- Administrative interfaces
- Messaging systems
- Intake and approval systems
- Searchable knowledge tools
- CRM improvements
- Better operational processes

Use the word **software** naturally throughout the site, but keep the “S” in GPS as **Solutions** because the right answer may include software, automation, process changes, or a combination.

### GPS Mashal

Use this prominently but not excessively:

> A GPS contains sophisticated technology, but the driver only needs to enter a destination and control the options that matter. Reuben approaches software the same way: he handles the complexity behind the scenes and gives the user simple, understandable controls.

Supporting line:

> **Powerful technology behind the scenes. Simple control in your hands.**

Important nuance: do not promise unlimited no-code customization. Promise that routine business variables, rules, prompts, templates, settings, and workflows can be managed without calling a developer for every adjustment.

#### Summary

> Built a self-service flyer generator that allows a nontechnical client to enter event details and instantly download a professionally formatted, print-ready PDF.

## 18. Technical Architecture

Use the existing stack where practical. Do not create unnecessary infrastructure.

### Frontend

If the current site uses Next.js/React, retain it.

Recommended:

- Next.js
- TypeScript
- Server-rendered public pages
- Responsive app shell for `/chat`
- Structured JSON or Markdown content source
- Accessible reusable components

### Chat Backend

Use a server-side API route or serverless function.

Requirements:

- API keys remain server-side.
- No unrestricted web access.
- No arbitrary tool execution.
- Rate limit requests.
- Limit input length.
- Add prompt-injection defenses.
- Add basic moderation.
- Log failures without unnecessarily storing private content.

### Retrieval

Do not begin with a large vector database unless needed.

Version one:

1. Classify the topic.
2. Retrieve relevant approved structured content.
3. Send only that context to the model.
4. Generate a grounded answer.
5. Attach relevant site links.

Add embeddings or vector search later only if the knowledge base becomes large enough to justify it.

### Conversation Storage

Default:

- No login.
- Store temporary chat state in memory/local storage.
- Provide “Clear conversation.”
- Do not store full server-side conversations unless explicitly required.
- If analytics are stored, minimize and anonymize them.

Optional later features—not required for v1:

- Email me this conversation
- Shareable read-only conversation
- Admin analytics for common questions

### Serverless Preference

Use low-operations, pay-per-use services. Avoid EC2 or a large persistent backend unless technically required.
